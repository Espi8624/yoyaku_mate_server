# ADR-007: シフト表を下書きと確定版に分離する

> 作成日: 2026-09-06
> ステータス: 採用
> 関連文書: [シフト表機能仕様書](../features/shift-table.md)、[シフト表実装詳細書](../implementation/shift-table.md)

---

## 背景 (Context)

シフト表は `(store_id, week_start_date)` ごとに1ドキュメントで、マネージャーとスタッフが同じドキュメントを読んでいた。マネージャーの編集は即座にサーバーへ反映されるため、**作りかけのシフト表がそのままスタッフに見えていた**。

具体的には次のいずれも、実行した瞬間に全スタッフの画面へ影響する状態だった。

* シフトブロックの追加 / 修正 / 削除
* 自動配置 (`auto-generate`)
* 修正依頼の一括適用 (`change-requests/apply`)

マネージャーが週の途中まで組んだ段階の表を見たスタッフが、確定していない予定で出勤日を誤認するおそれがある。「シフトを組み終えてから공開する」という区切りが、モデル上どこにも存在しなかった。

---

## 決定 (Decision)

`ShiftTable` に確定版を追加し、**編集は下書きにだけ効き、明示的な「確定」操作でのみスタッフへ公開される**ようにする。

```go
Shifts          []Shift    // 下書き: マネージャーが編集中
PublishedShifts []Shift    // 確定版: スタッフに公開されている
PublishedAt     *time.Time // nil = 一度も確定していない
```

* `GET` は呼び出し元の役割で返す版を変える。スタッフには確定版を `shifts` に載せ替えて返し、下書きは一切漏らさない。
* 公開は `POST .../publish` のみ。取り消しは `POST .../discard-draft`(下書きを確定版へ戻す。確定版自体は変更しない)。
* 修正依頼にも中間状態 `applied`(下書きへ反映済み・未確定)を追加し、確定と同時に `resolved` へ進める。スタッフ向けには `pending` に伏せて返す。

### 検討した代替案

**A. 単一バージョンのまま、リアルタイム通知を足す**
スタッフ画面へ SSE で更新を push する案。既存の SSE ブローカーを流用できるため実装は軽い。しかし**問題は「更新が遅れて伝わること」ではなく「未完成の状態が見えること」**なので、通知を速くしても解決しない。むしろ作りかけの状態がより速く伝わる。

**B. 下書きを別ドキュメント/別コレクションに分ける**
役割の分離は明確になるが、既存の編集エンドポイント5本すべてが書き込み先を切り替える必要があり、シフトの `_id` の一貫性も自前で管理することになる。得られるものに対して変更範囲が大きい。

**C. 同一ドキュメント内の2フィールドに持つ (採用)**
既存の `shifts` をそのまま下書きとして再利用できるため、**編集エンドポイントは1行も変えずに済む**。追加の書き込みは「確定」と「破棄」の2つだけで、どちらも配列のコピーで完結する。

---

## 帰結 (Consequences)

### 良い点

* スタッフに見えるのは常に確定版だけになり、作りかけが漏れない。
* 「確定」が唯一の公開点なので、マネージャーは公開タイミングを完全に制御できる。
* 既存の編集エンドポイントに手を入れていないため、退行のリスクが小さい。
* `discard-draft` により、確定後の編集を丸ごと取り消せる(削除の取り消し手段にもなる)。

### 悪い点・注意点

* **既存ドキュメントの移行が必須**。`published_at` の無いドキュメントは「未公開」と判定されるため、移行せずにデプロイすると公開済みだったシフト表が全スタッフから消える。マネージャー画面は正常に見えるため発見が遅れる。移行スクリプトは `scripts/migrate_shift_table_publish/` に用意した。
* 未確定判定は時刻比較では不正確なため、シフトの**内容比較**が必要になった(`shiftsContentEqual`)。削除して同じ内容を作り直すと `_id` だけが変わるため。
* 修正依頼のステータスが3状態になり、スタッフ向けレスポンスで `applied` を伏せる処理が必要になった。
* 確定してもスタッフ画面はリアルタイムに更新されない。クライアントはアプリ復帰時に `published_at` を確認して更新の有無だけを知らせ、取り込むかどうかはスタッフの操作に委ねている(常時接続は張らない)。
* `discard-draft` は最後の確定以降の変更を**すべて**戻す。1操作単位の undo ではない。
