# ADR-007: 시프트표를 초안과 확정본으로 분리

> 작성일: 2026-09-06
> 상태: 채택
> 관련 문서: [시프트표 기능 명세서](../features/shift-table.ko.md), [시프트표 구현 상세서](../implementation/shift-table.ko.md)

---

## 배경 (Context)

시프트표는 `(store_id, week_start_date)`마다 문서 하나였고, 매니저와 스태프가 같은 문서를 읽고 있었다. 매니저의 편집은 즉시 서버에 반영되므로 **작업 중인 시프트표가 그대로 스태프에게 보이고 있었다.**

구체적으로 다음은 모두 실행하는 순간 전 스태프의 화면에 영향을 주는 상태였다.

* 시프트 블록 추가 / 수정 / 삭제
* 자동배치 (`auto-generate`)
* 수정의뢰 일괄 적용 (`change-requests/apply`)

매니저가 주 중반까지만 짜놓은 표를 본 스태프가, 확정되지 않은 예정으로 출근일을 오인할 우려가 있다. 「시프트를 다 짜고 나서 공개한다」는 구분이 모델 어디에도 존재하지 않았다.

---

## 결정 (Decision)

`ShiftTable`에 확정본을 추가해, **편집은 초안에만 반영되고 명시적인 「확정」 조작으로만 스태프에게 공개**되도록 한다.

```go
Shifts          []Shift    // 초안: 매니저가 편집 중
PublishedShifts []Shift    // 확정본: 스태프에게 공개된 것
PublishedAt     *time.Time // nil = 한 번도 확정 안 됨
```

* `GET`은 호출자의 역할에 따라 반환 버전을 바꾼다. 스태프에게는 확정본을 `shifts`에 실어 반환하고 초안은 일절 노출하지 않는다.
* 공개는 `POST .../publish`만. 취소는 `POST .../discard-draft`(초안을 확정본으로 되돌림. 확정본 자체는 변경하지 않음).
* 수정의뢰에도 중간 상태 `applied`(초안에 반영됨·미확정)를 추가하고, 확정과 동시에 `resolved`로 진행한다. 스태프에게는 `pending`으로 가려 반환한다.

### 검토한 대안

**A. 단일 버전을 유지하고 실시간 통지를 추가**
스태프 화면으로 SSE 푸시를 보내는 안. 기존 SSE 브로커를 재사용할 수 있어 구현은 가볍다. 그러나 **문제는 「갱신이 늦게 전달되는 것」이 아니라 「미완성 상태가 보이는 것」**이므로, 통지를 빠르게 해도 해결되지 않는다. 오히려 작업 중인 상태가 더 빨리 전달된다.

**B. 초안을 별도 문서/별도 컬렉션으로 분리**
역할 분리는 명확해지지만, 기존 편집 엔드포인트 5개 전부가 쓰기 대상을 전환해야 하고 시프트 `_id`의 일관성도 직접 관리해야 한다. 얻는 것에 비해 변경 범위가 크다.

**C. 같은 문서 안의 두 필드로 보유 (채택)**
기존 `shifts`를 초안으로 그대로 재사용할 수 있어 **편집 엔드포인트를 한 줄도 바꾸지 않아도 된다.** 추가되는 쓰기는 「확정」과 「파기」 둘뿐이고, 둘 다 배열 복사로 끝난다.

---

## 결과 (Consequences)

### 좋은 점

* 스태프에게 보이는 것은 항상 확정본뿐이라 작업 중인 표가 새지 않는다.
* 「확정」이 유일한 공개 지점이므로, 매니저가 공개 시점을 완전히 통제할 수 있다.
* 기존 편집 엔드포인트를 건드리지 않아 회귀 위험이 작다.
* `discard-draft`로 확정 이후의 편집을 통째로 취소할 수 있다(삭제의 취소 수단도 된다).

### 나쁜 점·주의점

* **기존 문서의 마이그레이션이 필수다.** `published_at`이 없는 문서는 「미공개」로 판정되므로, 마이그레이션 없이 배포하면 공개돼 있던 시프트표가 전 스태프에게서 사라진다. 매니저 화면은 정상으로 보여 발견이 늦다. 마이그레이션 스크립트는 `scripts/migrate_shift_table_publish/`에 두었다.
* 미확정 판정은 시각 비교로는 부정확해서 시프트의 **내용 비교**가 필요해졌다(`shiftsContentEqual`). 삭제 후 같은 내용을 다시 만들면 `_id`만 바뀌기 때문이다.
* 수정의뢰 상태가 3단계가 되었고, 스태프용 응답에서 `applied`를 가리는 처리가 필요해졌다.
* 확정해도 스태프 화면은 실시간으로 갱신되지 않는다. 클라이언트는 앱 복귀 시 `published_at`을 확인해 갱신 유무만 알리고, 받아들일지는 스태프의 조작에 맡긴다(상시 연결은 사용하지 않음).
* `discard-draft`는 마지막 확정 이후의 변경을 **전부** 되돌린다. 1조작 단위 undo가 아니다.
