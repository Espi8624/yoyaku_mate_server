# 機能仕様書: シフト表 (Shift Table)

本文書は、`yoyaku_mate_server` に実装された店舗の週単位シフト表 (Shift Table) 機能仕様を定義します。

> 作成日: 2026-09-01
> 関連文書: [シフト表実装詳細書](../implementation/shift-table.md)、[スタッフ勤務可能時間機能仕様書](./staff-availability.md)

---

## 1. 概要 (Overview)

店舗マネージャーが週単位で各スタッフの勤務シフト(曜日・時間帯・担当スタッフ)を管理できる機能です。[スタッフ勤務可能時間](./staff-availability.md)機能で挙がっていた「シフト表の自動生成」の前段として、まずマネージャーが手動でシフトを組む機能を実装しました。

シフト表は週(月曜始まり)ごとに独立したドキュメントで管理され、**マネージャーが明示的に作成しない限り、その週のシフト表は存在しません**。未作成の週を照会した場合は「未作成」として扱われます。

---

## 2. 主な機能 (Key Features)

1. **週単位のシフト表作成 (マネージャー専用)**:
   - 対象週の月曜日の日付を指定して、空のシフト表を新規作成します。
   - 既に同じ週のシフト表が存在する場合は作成できません(重複作成の防止)。
2. **シフトの追加/修正/削除 (マネージャー専用)**:
   - 作成済みのシフト表に対し、スタッフ・曜日・開始/終了時刻を指定してシフトを1件単位で追加/修正/削除します。
   - シフトに割り当てられるスタッフは、当該店舗の承認済み (`APPROVED`) スタッフに限られます。
3. **シフト表の照会 (マネージャー / 承認済みスタッフ)**:
   - マネージャーおよび承認済みスタッフは、週を指定してシフト表(登録済みシフト一覧)を照会できます。
   - 照会のみはスタッフにも許可されますが、作成・追加・修正・削除はマネージャーのみ可能です。
4. **下書きと確定の分離 (マネージャー専用)**:
   - マネージャーの編集・自動配置・修正依頼の適用は全て**下書き**にだけ効きます。
   - 「確定」を押した時点で下書きが確定版へコピーされ、初めてスタッフに公開されます。

---

## 3. 下書きと確定 (Draft / Publish)

シフト表は「マネージャーが編集中の下書き」と「スタッフに公開されている確定版」の2本立てで保持します。作りかけのシフト表がスタッフに見えてしまうと、確定していない予定で出勤日を誤認させるおそれがあるためです。

| 操作 | 効く先 | スタッフから見えるか |
|---|---|---|
| シフトの追加/修正/削除 | 下書き | 見えない |
| 自動配置 (auto-generate) | 下書き | 見えない |
| 修正依頼の適用 (change-requests/apply) | 下書き | 見えない |
| **確定 (publish)** | 下書き → 確定版 | **ここで公開される** |
| 下書きの破棄 (discard-draft) | 確定版 → 下書き | 見えない (確定版は不変) |

* スタッフ向けの `GET` は常に確定版を返します。一度も確定していない週は「未作成」と同じ `404` を返し、クライアントは既存の空状態表示をそのまま使います。
* マネージャー向けの `GET` は下書きを返し、未確定の変更が残っているかを `has_unpublished_changes` で伝えます。
* `has_unpublished_changes` はタイムスタンプではなく**内容比較**で判定します (`_id` は無視)。削除して同じ内容を作り直しただけの場合に「未確定の変更あり」と誤表示しないためです。加えて、後述の `applied` な修正依頼が1件でも残っていれば `true` になります。

### 修正依頼のステータス連動

修正依頼も同じ原則に従い、`pending` → `applied` → `resolved` の3状態を持ちます。

| ステータス | 意味 | スタッフからの見え方 |
|---|---|---|
| `pending` | 未対応 | 未対応 |
| `applied` | 下書きへ反映済み・**未確定** | `pending` に伏せて返す |
| `resolved` | 確定済み | 対応済み |

適用しただけで「対応済み」と見せると、スタッフのシフト表は変わっていないのに対応が完了したと誤解されます。そのため `applied` はマネージャーにしか見えず、確定と同時に `resolved` へ進みます。

## 4. データ構造 (Shift Table Schema)

```json
{
  "_id": "66f1...",
  "store_id": "store_abc",
  "week_start_date": "2026-09-07",
  "shifts": [
    {
      "_id": "66f2...",
      "staff_id": "66e0...",
      "day": "monday",
      "start_time": "09:00",
      "end_time": "17:00"
    }
  ],
  "published_shifts": [],
  "published_at": "2026-09-06T12:00:00Z"
}
```

* `shifts` は下書き、`published_shifts` は確定版。どちらも同じ Shift 構造です。
* `published_shifts` は DB 上のフィールドで、API レスポンスには現れません。`shifts` に「その利用者が見るべき版」を載せ替えて返すため、クライアントは両者を区別せず描画できます。
* `published_at` が `null` (未設定) の週は一度も確定されておらず、スタッフには未公開です。
* `week_start_date` はその週の月曜日を表す `YYYY-MM-DD` 形式の文字列。月曜日以外の日付は不正値として拒否されます。
* `day` は [スタッフ勤務可能時間](./staff-availability.md)と同じ曜日キー体系 (`monday`〜`sunday`)。
* `start_time` / `end_time` は `HH:MM` (24時間表記) 形式で、`start_time < end_time` である必要があります。

## 5. API 仕様 (API Specification)

### `GET /api/stores/{storeId}/shift-tables/{weekStartDate}`

* **説明**: 指定週のシフト表を取得します。呼び出し元の役割によって返す版が変わります。
* **権限**: マネージャー、または承認済みスタッフ。
* **レスポンス**:
  * マネージャー: `200 OK` — `shifts` に下書き、`has_unpublished_changes` に未確定フラグ。
  * スタッフ: `200 OK` — `shifts` に確定版。一度も確定していない週は `404 Not Found`。
  * `404 Not Found` — その週にシフト表が未作成。

### `POST /api/stores/{storeId}/shift-tables/{weekStartDate}/publish`

* **説明**: 下書きを確定し、スタッフに公開します。同時に `applied` な修正依頼を `resolved` へ進めます。
* **権限**: マネージャーのみ。
* **リクエストボディ**: なし。
* **レスポンス**: `200 OK` — `{ "shift_table": { ... }, "resolved_request_count": 2 }`。`404 Not Found` — シフト表が未作成。

### `POST /api/stores/{storeId}/shift-tables/{weekStartDate}/discard-draft`

* **説明**: 下書きを破棄し、確定版の内容へ戻します。確定版そのものは変更しないため、スタッフに見えているシフト表はこの操作では変わりません。同時に `applied` な修正依頼を `pending` へ戻します (反映先の下書きを捨てる以上、反映済みの状態だけを残せないため)。一度も確定していない週は「空のシフト表」が戻し先になります。
* **権限**: マネージャーのみ。
* **リクエストボディ**: なし。
* **レスポンス**: `200 OK` — `{ "shift_table": { ... }, "reverted_request_count": 1 }`。`404 Not Found` — シフト表が未作成。

### `POST /api/stores/{storeId}/shift-tables`

* **説明**: 指定週の空のシフト表を新規作成します。
* **権限**: マネージャーのみ。
* **リクエストボディ**: `{ "week_start_date": "2026-09-07" }`
* **レスポンス**: `201 Created`。`409 Conflict` — 既に同じ週のシフト表が存在する場合。

### `POST /api/stores/{storeId}/shift-tables/{weekStartDate}/shifts`

* **説明**: シフトを1件追加します。
* **権限**: マネージャーのみ。
* **リクエストボディ**: `{ "staff_id": "...", "day": "monday", "start_time": "09:00", "end_time": "17:00" }`
* **レスポンス**: `201 Created`。`404 Not Found` — シフト表が未作成の場合(先に作成が必要)。

### `PATCH /api/stores/{storeId}/shift-tables/{weekStartDate}/shifts/{shiftId}`

* **説明**: 既存シフトを1件更新します。
* **権限**: マネージャーのみ。
* **リクエストボディ**: `POST /shifts` と同様。

### `DELETE /api/stores/{storeId}/shift-tables/{weekStartDate}/shifts/{shiftId}`

* **説明**: 既存シフトを1件削除します。
* **権限**: マネージャーのみ。

## 6. クライアントUI

`yoyaku_mate_provider` のスタッフ管理画面は2ページ構成になっており、ページ1(スタッフ管理)を右にスワイプするとページ2(シフト表)に切り替わります。シフト表画面は Outlook / Microsoft Teams の週間カレンダー表示を参考にした、曜日×時間のグリッドUIです。詳細は [クライアント側実装詳細書](../../../yoyaku_mate_provider/docs/implementation/shift-table.md) を参照。

---

## 7. 今後の計画 (Roadmap)

スタッフへの公開は「確定」を押した時点でのシフト表の写しを配るだけで、スタッフ側の画面へリアルタイムに通知する仕組み (SSE / プッシュ通知) はまだありません。スタッフは画面を開き直した時に最新の確定版を取得します。
