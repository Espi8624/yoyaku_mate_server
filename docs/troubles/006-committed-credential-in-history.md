## 経緯

GitGuardianから "1 internal secret incident detected" (Generic Password, コミット
`41b056d`) の通知を受けた。確認したところ**通知自体は誤検知**だったが、
ついでに履歴全体を洗ったところ**本物の漏洩が見つかった。**

つまりこの記録の主眼は漏洩そのものよりも、
**[004](./004-production-readiness-hardening.md) で「シークレットのコミット無し」と
判断した点検が、なぜこれを見落としたか**にある。

## 1. 通知自体は誤検知だった

`41b056d` (「MongoDB接続文字列をログへ平文で出さないようにする」) で追加した
`db/mongo_test.go` のテストフィクスチャが検知されていた。

```go
const password = "s3cr3tP4ssw0rd"
uri: "mongodb+srv://appuser:" + password + "@cluster0.example.mongodb.net/project_rusui?..."
```

**maskMongoURI が認証情報を正しく伏せるかを検証するテスト**が検知された形である。
ホストは `cluster0.example.mongodb.net` (例示用の予約ドメイン)、ユーザーは `appuser`、
パスワードは一目でダミーと分かる文字列。対応不要。

シークレットスキャナーにこの種の誤検知は構造的についてくる。
**認証情報を扱うコードのテストは、必ず認証情報の形をした文字列を含むからである。**

## 2. 洗っていたら本物が出てきた

```
config.development.json:3:
  "uri": "mongodb+srv://taishi11291208:<16文字のパスワード>@cluster0.3bifxsy.mongodb.net/?retryWrites=true&w=majority"
```

| 項目 | 内容 |
|---|---|
| 追加 | `3172d1c` |
| 削除 | `379d149` (2025-10-25) — **ワーキングツリーからのみ**削除 |
| 残存 | 履歴 **51コミット** |
| リポジトリ | 当時public (`Espi8624/yoyaku_mate_server`) |

### 危険度: 低い (クラスターが既に無い)

```
_mongodb._tcp.cluster0.3bifxsy.mongodb.net → NXDOMAIN   (漏洩した方、消滅)
_mongodb._tcp.cluster0.fbah1dz.mongodb.net → 正常応答     (現在のdev)
```

漏洩したのは**現在使っていない旧クラスター**の認証情報で、そのクラスターは既に
削除されており存在しない。現在のdevは別クラスター・別ユーザー (`espi8624`) を使う。
接続先が無いため、この認証情報単体では何もできない。

**残るリスクはパスワードの使い回しだけである。** その文字列を他のAtlasユーザーや
別のサービスでも使っていれば、そちらが露出しているのと同じことになる。

### 履歴の書き換えは行わないことにした

BFGや `git filter-repo` で51コミットを書き換える選択肢はあるが、採らなかった。

- public期間があった以上、既にクローン・フォーク・インデックスされた可能性は戻せない。
  **書き換えても「漏れていない状態」には戻らない**
- 一方でコストは確実に発生する。既存のクローンが全て壊れ、`develop`/`main` への
  force-pushが必要になる
- そして**消そうとしている対象が既に死んだ認証情報である**

認証情報がまだ生きていたなら判断は逆になる。その場合は書き換えより**まずローテーション**。
書き換えには時間がかかり、その間もキーは有効なままだからである。

## 3. 004の点検はなぜ見落としたか

004にはこう書かれていた。

> - **シークレットのコミット**: 履歴上も無し

2点で誤っていた。そして**その誤り方は繰り返されやすい種類**のものである。

**(a) 「履歴上も」と書きながら、実際には現時点しか見ていなかった。**
`git ls-files` も `git grep` (リビジョン未指定) も**ワーキングツリーしか見ない**。
削除済みのファイルはどちらにも現れない。履歴を見るにはリビジョンの明示が要る。

```bash
# 現在しか見ない — 削除済みファイルは見えない
git grep -n "mongodb+srv://"

# 履歴全体を見る
git grep -n "mongodb+srv://" $(git rev-list --all)
```

**(b) `.gitignore` を信頼した。**
`.gitignore` には `config/` があったが、コミットされたファイル名はスラッシュではなく
ドットの `config.development.json` だった。**一文字の違いでルールをすり抜けていた。**

同じ理由で今回の調査でも最初は見落としかけた。はじめに `config/development.json` で
検索して「履歴に無し」と結論づけ、パターンベース (`mongodb+srv://`) で洗い直して
ようやく発見している。

> **パスやファイル名で探さず、内容のパターンで探すこと。**
> パスはタイポひとつ、ドットひとつですり抜ける。`mongodb+srv://`、`AIza`、
> `BEGIN PRIVATE KEY` のような値の形はすり抜けない。

**(c) GitGuardianは過去のコミットを見ていなかった。**
連携以降の新規コミットのみをスキャンする設定のため、2025年の本物の漏洩は捕まえられず、
2026年のテストフィクスチャだけを捕まえた。過去コミットのスキャン (historical scan) は
別途有効化が必要である。

## あわせて確認したこと

4リポジトリ全体を同じパターンで洗った。

| 対象 | 結果 |
|---|---|
| `yoyaku_mate` (顧客ウェブ) | シークレット無し。`.env.production` はAPI URLとESLintフラグのみ |
| `yoyaku_mate_admin` | シークレット無し |
| `yoyaku_mate_provider` | Firebaseクライアントキーあり (`ios/Runner/GoogleService-Info.plist`, `public/verify.html`)。**設計上公開されてよい値**なので漏洩ではない |
| `yoyaku_mate_server` | 上記の件 |

Gemini APIキーは**どのリポジトリの履歴にも無い。** サーバー移行前もクライアントの
`.env` はコミットされていなかった。

ただしproviderの `GoogleService-Info.plist` は、**CLAUDE.mdにgitignore対象と
書かれているのに実際には追跡されている。** キー自体は問題ないが、記述と実態が食い違っている。

## 残る対応 (コンソール作業)

1. GitGuardianで `41b056d` を誤検知として処理 + テストパスの除外設定
2. **GitGuardianの過去コミットスキャンを有効化** — 有効にしない限り同種をまた見落とす
3. 漏洩したパスワードを他でも使っていないか確認 → 使っていれば変更
4. リポジトリのprivate化 (予定)

## 教訓

- **「履歴を確認した」と書く前に、本当に履歴を見たか確認する。**
  `git grep` はリビジョンを与えなければ現在しか見ない。削除済みファイルが見えないのはそのため
- **パスではなく値の形で探す。** `.gitignore` も検索もパスベースだと、
  `config/` と `config.` のように一文字の違いですり抜ける
- **点検結果を「問題なし」と記録するときが最も危うい。** その記録があると、
  次に見る人は同じ場所を調べ直さない。004の「問題が無かった場所」一覧は再調査を
  減らすために作ったものだが、誤った項目が一つ混ざった途端、そこだけを正確に隠した
- **認証情報が生きているなら、履歴の書き換えよりローテーションが先。** 書き換えには
  時間がかかり、その間もキーは有効で、既に広まった複製は取り戻せない
