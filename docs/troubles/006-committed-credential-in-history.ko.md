# 006: 히스토리에 남아 있던 Atlas 자격증명과, 그것을 놓친 점검 방법

> 작성일: 2026-09-18
> 상태: 조사 완료 / 유출된 클러스터는 이미 소멸, 잔여 조치는 콘솔 작업
> 관련: [004](./004-production-readiness-hardening.ko.md)(오판한 점검), [`db/mongo_test.go`](../../db/mongo_test.go)

---

## 경위

GitGuardian에서 "1 internal secret incident detected"(Generic Password, 커밋 `41b056d`)
알림을 받았다. 확인해보니 **알림 자체는 오탐**이었지만, 확인하는 김에 히스토리 전체를
훑다가 **진짜 유출을 발견했다.**

즉 이 문서의 요점은 유출 그 자체보다 **[004](./004-production-readiness-hardening.ko.md)에서
"시크릿 커밋 없음"이라고 판단했던 점검이 왜 이걸 놓쳤는가**에 있다.

---

## 1. 알림 자체는 오탐이었다

`41b056d`("MongoDB接続文字列をログへ平文で出さないようにする")에 추가된
`db/mongo_test.go`의 테스트 픽스처가 탐지됐다.

```go
const password = "s3cr3tP4ssw0rd"
uri: "mongodb+srv://appuser:" + password + "@cluster0.example.mongodb.net/project_rusui?..."
```

**`maskMongoURI`가 자격증명을 제대로 가리는지 검증하는 테스트**가 탐지된 것이다.
호스트는 `cluster0.example.mongodb.net`(예시용 예약 도메인), 계정은 `appuser`,
비밀번호는 한눈에 더미인 문자열이다. 조치 불필요.

시크릿 스캐너에 이런 종류의 오탐은 구조적으로 따라온다.
**자격증명을 다루는 코드의 테스트는 반드시 자격증명 형태의 문자열을 포함하기 때문이다.**

## 2. 그런데 훑다가 진짜가 나왔다

```
config.development.json:3:
  "uri": "mongodb+srv://taishi11291208:<16자 비밀번호>@cluster0.3bifxsy.mongodb.net/?retryWrites=true&w=majority"
```

| 항목 | 내용 |
|---|---|
| 추가 | `3172d1c` |
| 삭제 | `379d149` (2025-10-25) — **작업 트리에서만** 삭제 |
| 잔존 | 히스토리 **51개 커밋** |
| 저장소 | 당시 공개 (`Espi8624/yoyaku_mate_server`) |

### 위험도: 낮음 (클러스터가 이미 없다)

```
_mongodb._tcp.cluster0.3bifxsy.mongodb.net → NXDOMAIN   (유출된 쪽, 소멸)
_mongodb._tcp.cluster0.fbah1dz.mongodb.net → 정상 응답   (현재 dev)
```

유출된 것은 **지금 쓰지 않는 옛 클러스터**의 자격증명이고, 그 클러스터는 이미 삭제되어
존재하지 않는다. 현재 dev는 다른 클러스터·다른 계정(`espi8624`)을 쓴다.
접속할 대상이 없으므로 이 자격증명 자체로는 아무것도 할 수 없다.

**남은 위험은 비밀번호 재사용 하나뿐이다.** 그 문자열을 다른 Atlas 계정이나
다른 서비스에서도 쓰고 있다면 그쪽이 노출된 것과 같다.

### 히스토리 재작성은 하지 않기로 했다

BFG나 `git filter-repo`로 51개 커밋을 다시 쓰는 선택지가 있지만 채택하지 않았다.

- 공개 기간이 있었으므로 이미 클론·포크·인덱싱됐을 가능성을 되돌릴 수 없다.
  **재작성해도 "유출되지 않은 상태"로는 돌아가지 않는다**
- 반면 비용은 확실하다. 기존 클론이 전부 깨지고, `develop`/`main`에 force-push가 필요하다
- 그리고 **지우려는 대상이 이미 죽은 자격증명이다**

자격증명이 아직 살아 있었다면 판단은 반대가 된다. 그때는 재작성보다 **먼저 로테이션**이다.
재작성은 시간이 걸리고 그동안에도 키는 유효하기 때문이다.

## 3. 004의 점검은 왜 이걸 놓쳤나

004에는 이렇게 적혀 있었다.

> - **시크릿 커밋**: 히스토리상으로도 없음
>   (`config.development.json`은 추적되고 있으나 자격증명 미포함)

두 군데가 틀렸다. 그리고 **틀린 방식이 반복되기 쉬운 종류**다.

**(a) "히스토리상으로도"라고 쓰고 실제로는 현재 시점만 봤다.**
`git ls-files`도 `git grep`(리비전 미지정)도 **작업 트리만** 본다.
삭제된 파일은 어느 쪽에도 나오지 않는다. 히스토리를 보려면 리비전을 명시해야 한다.

```bash
# 현재만 본다 — 삭제된 파일은 안 보인다
git grep -n "mongodb+srv://"

# 히스토리 전체를 본다
git grep -n "mongodb+srv://" $(git rev-list --all)
```

**(b) `.gitignore`를 믿었다.**
`.gitignore`에는 `config/`가 있었지만, 커밋된 파일명은 슬래시가 아니라 점이 들어간
`config.development.json`이었다. **한 글자 차이로 규칙을 비껴갔다.**

같은 이유로 이번 조사에서도 처음엔 놓칠 뻔했다. 처음에 `config/development.json`으로
검색해 "히스토리에 없음"이라고 결론 냈다가, 패턴 기반(`mongodb+srv://`)으로 다시
훑고 나서야 발견했다.

> **경로나 파일명으로 찾지 말고 내용 패턴으로 찾을 것.**
> 경로는 오타 하나, 점 하나로 빠져나간다. `mongodb+srv://`, `AIza`,
> `BEGIN PRIVATE KEY` 같은 값의 형태는 빠져나가지 않는다.

**(c) GitGuardian은 과거 커밋을 보고 있지 않았다.**
연동 이후의 신규 커밋만 스캔하는 설정이라, 2025년의 진짜 유출은 잡지 못하고
2026년의 테스트 픽스처만 잡았다. 과거 커밋 스캔(historical scan)은 별도로 켜야 한다.

## 함께 확인한 것

4개 저장소 전체를 같은 패턴으로 훑었다.

| 대상 | 결과 |
|---|---|
| `yoyaku_mate` (고객 웹) | 시크릿 없음. `.env.production`은 API URL과 ESLint 플래그뿐 |
| `yoyaku_mate_admin` | 시크릿 없음 |
| `yoyaku_mate_provider` | Firebase 클라이언트 키 있음 (`ios/Runner/GoogleService-Info.plist`, `public/verify.html`). **설계상 공개되어도 되는 값**이므로 유출이 아니다 |
| `yoyaku_mate_server` | 위의 건 |

Gemini API 키는 **어느 저장소 히스토리에도 없다.** 서버 이전 전에도 클라이언트의
`.env`는 커밋되지 않았다.

다만 provider의 `GoogleService-Info.plist`는 **CLAUDE.md에 gitignore 대상이라고
적혀 있는데 실제로는 추적되고 있다.** 키 자체는 문제없지만 문서와 현실이 어긋나 있다.

## 교훈

- **"히스토리를 확인했다"고 쓰기 전에, 정말 히스토리를 봤는지 확인할 것.**
  `git grep`은 리비전을 주지 않으면 현재만 본다. 삭제된 파일은 그래서 안 보인다
- **경로가 아니라 값의 형태로 찾을 것.** `.gitignore`도 검색도 경로 기반이면
  `config/` 와 `config.` 처럼 한 글자 차이로 빠져나간다
- **점검 결과를 "문제 없음"으로 기록할 때가 가장 위험하다.** 그 기록이 있으면
  다음 사람은 같은 곳을 다시 보지 않는다. 004의 "문제가 없던 곳" 목록은 재조사를
  줄이려고 만든 것인데, 틀린 항목이 하나 섞이자 그 부분만 정확히 가려버렸다
- **자격증명이 살아 있다면 히스토리 재작성보다 로테이션이 먼저다.** 재작성은
  시간이 걸리고 그동안에도 키는 유효하며, 이미 퍼진 복제본은 되돌릴 수 없다
